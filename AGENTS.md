# AlfredAI Flutter Agent Guidelines

## Scope
These instructions apply to the entire repository unless a nested `AGENTS.md` overrides a portion of the guidance. Add more specific instructions in subdirectories whenever you introduce new architectural areas (for example, a specialized package inside `lib/`).

## Repository overview
- This is a Flutter application that targets Android first, but it also includes the scaffolding for iOS, desktop, and web platforms.
- Real‑time AI functionality depends on the `openai_realtime_dart` package found in the `langchain_dart/packages/openai_realtime_dart` submodule. Do not modify submodule code from this repository unless instructed; instead, contribute upstream when changes are required.
- Sensitive configuration lives in `.env`. Never commit credentials. Use placeholders or clearly documented environment variables when updating documentation.

## General workflow
1. Prefer incremental, well‑scoped changes. Document behavior changes in the relevant README or inline comments when necessary.
2. Keep the code self‑documenting. Only add comments when they clarify intent that is not obvious from the implementation.
3. Favor descriptive commit messages and keep the history clean (no merge commits in feature branches unless directed).

## Dart & Flutter code style
- Run `dart format` (or `flutter format`) on any Dart files you change. The CI and lint rules assume formatted code.
- Respect the lint configuration from `analysis_options.yaml` (which includes `flutter_lints`). Silence individual lint rules only with `// ignore:` directives and include a justification comment when you do.
- Keep widget build methods pure—avoid side effects in `build()` and prefer using lifecycle hooks (`initState`, `dispose`, etc.) for imperative work.
- Extract reusable UI pieces into widgets under `lib/` to keep files focused and maintainable. Co-locate widgets with related logic when practical.
- Use `const` constructors and widgets wherever possible to improve performance.
- Favor strongly typed APIs and immutable data objects. If you introduce new models, implement `==`/`hashCode` (or use `equatable`/`freezed` if already adopted).

## State management & async patterns
- The current codebase uses platform channels, WebRTC, and shared preferences. Maintain existing patterns unless a refactor is explicitly requested.
- When dealing with asynchronous work (streams, futures), prefer `async`/`await` syntax and ensure proper error handling and cleanup to avoid resource leaks.
- For audio or WebRTC features, ensure permissions are requested via `permission_handler` before invoking APIs that require them.

## Assets & configuration
- Declare new assets in `pubspec.yaml` under the `flutter/assets` section and keep file paths consistent.
- Store secrets only in `.env`. If you need a new variable, document its purpose in the README.
- When adding platform-specific setup (Android/iOS/desktop/web), document the manual steps in `README.md` or a dedicated markdown file.

## Testing & quality gates
- Run `flutter analyze` and `flutter test` after making Dart or Flutter changes. Include the commands and their results in the final report.
- Prefer writing or updating widget/unit tests in `test/` when you introduce new functionality or fix a bug. Keep tests deterministic and isolated.
- For UI changes that impact the rendered interface, capture a screenshot (using the provided tooling) when feasible.

## Platform-specific guidance
- Android is the only platform verified today. When modifying Android code, ensure Gradle builds succeed and note any required manual configuration changes.
- iOS, desktop, and web folders are largely the defaults generated by Flutter. If you change them, follow the respective platform conventions and document new steps clearly.

## Documentation
- Keep `README.md` synchronized with new capabilities or setup instructions.
- When introducing complex flows or new services, add developer notes (e.g., in a `docs/` directory) to aid future contributors.

## Pull requests
- Provide concise, informative descriptions summarizing motivation, implementation approach, and testing evidence.
- Group related changes together; avoid bundling unrelated refactors or formatting updates with feature work.
